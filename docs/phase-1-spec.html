1Goal & boundary

Ship a usable relationship system of record in one focused build, on a standalone service, that a relationship manager would open every day even if no AI ran at all.

The v1.0 blueprint describes 13 phases ending in an autonomous, self-improving agent. Phase 1 deliberately stops at the stable base the blueprint itself calls the prerequisite: “The first usable product should already manage organizations, officials, relationships, interactions and follow-ups. AI and autonomy are then layered onto a stable system of record.”

AI appears in Phase 1 in exactly one place — turning interaction notes into structured fields, and drafting greetings for detected moments. Every outbound message is a draft a human sends by hand. There is no agent runtime, no tool-calling loop, no memory store, no strategy versioning.

Why this cut

The learning loop needs months of real outcome data before it can evaluate anything, and autonomous sending to real officials is a reputational risk that isn't worth carrying on day one. Both get their own phase later, on top of this base.

2Scope & non-goals

In scope — Phase 1

  • Auth + RBAC: three roles — Admin, Relationship Manager, Approver/Viewer
  • Configurable organisation hierarchy (Head Office / Regional Office / Zonal Office / Area Office / Branch + future types), tree explorer
  • Official profiles: identity, posting, level, unit, source, confidence, verification status, timeline
  • Relationship record per (official, owner): lifecycle status, importance, transparent health score + history
  • Interaction & meeting log; AI summary → schema-validated fields (attendees, topics, commitments, sentiment) with human override
  • Tasks & follow-ups from commitments; due dates, reminders, overdue flag, escalation
  • Engagement moments: promotion / birthday / work-anniversary → draft greeting + “Why now?” evidence + fatigue check
  • Excel/CSV import: validate → preview → dedupe → confidence → verify → commit
  • Executive dashboard: coverage, avg health, at-risk count, overdue follow-ups, pending drafts, upcoming moments
  • Audit log on every mutation and every AI action

Explicitly not in Phase 1

  • Autonomous agent — supervisor, planner, tool runtime, event-reaction loop
  • Memory architecture — short-term / episodic / semantic / strategic stores
  • Learning & recursive improvement — strategy registry, versions, experiments, promotion/rejection
  • RAG question-answering over notes and documents
  • Opportunity pipeline (detection, stages, conversion) — deferred to Phase 2
  • Predictive / ML relationship-risk scoring — rules only until data exists
  • Any automated external send; any scheduled outbound. Drafts only, sent from the mailbox by a person
  • Public-source enrichment / scraping of officials’ personal data
  • Coupling to MIRA or the report dashboard — this is a standalone service

5Relationship score

A transparent weighted sum, 0–100, recomputed on every new interaction, follow-up completion, or nightly. The blueprint's weight set includes an opportunity activity signal; Phase 1 has no opportunities, so its 20 points are redistributed and the change is recorded as a named weight version.

SignalBlueprint weightPhase 1 weightSource in Phase 1
Interaction recency20%25%relationships.last_interaction_at
Interaction frequency20%25%count of interactions in trailing 90 days
Response / engagement15%20%replies logged against outbound interactions
Meeting activity15%15%interactions.type = meeting, trailing 180 days
Opportunity activity20%—deferred to Phase 2
Follow-up completion10%15%done ÷ total tasks, trailing 90 days

Design rule

Weights live in config, not code, and every stored score references the weight version that produced it. When the learning phase later wants to test alternative weights, nothing about the schema has to change.

6Engagement moments

The moment pipeline is the one place Phase 1 touches outreach, and it stops at a draft. Flow:

STRUCTURED FIELD CHANGE → DETECT MOMENT → RELATIONSHIP CONTEXT → APPROPRIATENESS → FATIGUE CHECK → DRAFT → HUMAN APPROVES → SENT BY HAND → OUTCOME LOGGED
MomentTrigger in Phase 1Draft
Promotion / new postingofficial_dates.kind = promoted added, or designation change with sourcepersonalised congratulations
Birthdaykind = birthday, value known and verified, within 7 daysshort professional greeting
Work anniversarykind = joined, whole-year multiple within 7 daysbrief acknowledgement
Relationship inactivityno interaction 35+ days on an ACTIVE+ relationshipnon-sales check-in prompt (task, not message)

“Why now?” panel

Every moment card exposes its evidence: the triggering field change and its source, days since last interaction, last sentiment, relationship band. No recommendation appears without this.

Communication fatigue

Before a draft is offered, suppress if the official has had contact within a configurable window (default 21 days) or an open draft already exists. The objective is relationship quality, not message volume.

Hard constraint

No moment ever advances past draft_ready automatically. There is no scheduler that sends, and no credential path that could send, in Phase 1. A person copies the draft into the mailbox and sends it.

7Data ingestion

UPLOAD → VALIDATE → NORMALISE → RESOLVE → DEDUPE → CONFIDENCE → PREVIEW → VERIFY → COMMIT

Structured inputs for Phase 1: Excel, CSV, manual entry. Meeting notes and documents are captured through the interaction log, not the bulk importer.

Email threads

Two ways in, both landing as interactions rows: paste raw email text into the capture screen, or upload an .eml file (single message or a forwarded thread). The parser pulls from / to / date / subject and the body, strips quoted history into a collapsed block, and attempts to match the sender address to an existing official — the operator confirms or picks the official and relationship before save. Same AI extraction then runs on the body as on typed notes.

Entity resolution

Matching signals: name similarity, designation, department, location, organisation unit, existing identifiers. A row is auto-merged only when multiple signals agree; a name match alone is never sufficient.

From past mistakes

Dedupe on (name, email) together, never name alone — one name legitimately maps to several distinct people. And always render one sample of the resolved output in the preview step before the operator commits a bulk apply; this has caught real errors before.

Provenance

Every enriched field stores: value → source → source_date → confidence → verification_status → verified_by → verified_at. Unverified fields are visually flagged in the UI and excluded from moment triggers.

9Screens

  1. Executive dashboard — coverage, average health, at-risk count, overdue follow-ups, pending drafts, and a feed of moments in the next 7 days.
  2. Organisation explorer — the organisation tree, expand/collapse, unit detail with its officials and departments.
  3. Official profile — identity + posting, per-field source/verification badges, relationship timeline, linked interactions, tasks and moments.
  4. Relationship detail — status, importance, score with its component breakdown and history sparkline, next action.
  5. Interaction capture — paste notes, see AI summary and structured fields side by side, edit before save.
  6. Follow-up queue — all open tasks, sortable by due date, overdue highlighted, escalation visible.
  7. Moments feed — detected moments, each with its “Why now?” evidence, draft editor, approve / dismiss.
  8. Import centre — upload, validation results, resolved-row preview with a worked sample, verify, commit.

Rules that apply to every module

  • Standalone. Its own repo, database and deployment. No import from MIRA or the report dashboard.
  • Draft-only. No code path sends external mail. No live-credential “smoke test” ever runs against a real mailbox.
  • Configurable hierarchy. Unit types and levels are data. No business logic branches on a literal level name.
  • Structured AI output. Every extraction returns a validated object; parsing free text downstream is a bug.
  • Provenance everywhere. Enriched fields keep source, confidence and verification state; unverified data can't trigger a moment.
  • Audit everything. Every mutation and every AI action writes who / what / when / why / source / result.
  • Kill switch. A feature flag disables moment detection and drafting without a deploy.
  • Backend restarts clean. Kill and restart after Python changes rather than trusting reload.

11Sub-phases & Definition of Done

Built vertically — each sub-phase ends with something a user can actually open. Calendar estimate is 6–10 weeks for one developer working AI-assisted, not the blueprint's optimistic 25–35 days.

1A Foundation~1 wk

Repo, Docker, Postgres, Alembic, React shell, auth, RBAC, audit-log plumbing, CI running tests.

1B Organisation & officials~1.5 wk

Configurable hierarchy, tree explorer, official CRUD with search / filter, per-field source and verification state, profile timeline.

1C Relationships & interactions~2 wk

Relationship entity + lifecycle, weighted score + history + bands, interaction log with AI summary and structured extraction, sentiment.

1D Follow-ups & ingestion~2 wk

Tasks from commitments, reminders, overdue sweep, escalation. Excel/CSV import with validation, entity resolution, dedupe, worked-sample preview, verification, commit.

1E Moments & dashboard~1.5 wk

Moment detection from structured fields, “Why now?” evidence, fatigue suppression, draft editor, approve / dismiss. Executive dashboard and relationship-health report. Hardening, runbook, demo data.

A sub-phase is done when…

  • the feature is implemented and its unit + API tests pass
  • it is wired into the UI and reachable from navigation
  • mutations and AI actions write audit rows
  • it is documented in the repo
  • it is demonstrated end-to-end with realistic sample data
  • AI outputs in it are schema-validated and have an eval fixture

12Decisions

Resolved 7 September 2026. One item stays parked until deployment.

QuestionDecision for Phase 1
Data sourcing Excel + manual entry + email threads (paste and .eml) only. Load data gradually via the import flow.
Auth Local email + password. Three roles, no SSO. Not deployed this phase.
LLM Open model behind a provider-independent wrapper. Dev on local Ollama (small instruct model); production default chosen at 1E by running the eval fixture against a larger open model. Model name is config — never a code dependency.
Language Mixed English + Hindi (Devanagari and romanised). Prompts handle both. Enum fields (type, status, sentiment) normalise to English; free-text fields (topics, commitments) are kept verbatim. Eval fixture includes Hindi and mixed samples.
Users One small team (assume 2–5 relationship managers). Admin — users, org hierarchy, verification. Relationship Manager — owns and edits own relationships, reads all. Approver / Viewer — reads, approves or dismisses drafts. No per-object permissions beyond ownership.
Relationship owner Admin-assigned. A manager may self-claim an unowned relationship; an Admin can reassign. Recorded in the audit log.
Importance Owner-set enum — Routine / Important / Strategic — pre-filled on creation from the official's level (senior grades → Strategic) and override-able.
Verification A manager attaches a value with its source as unverified; an Admin flips it to verified. No mandatory second reviewer in Phase 1. Every change writes an audit row, so a review step can be added later with no schema change.
Hosting · parked Decided at deployment. Standalone does not require separate hardware from MIRA.
